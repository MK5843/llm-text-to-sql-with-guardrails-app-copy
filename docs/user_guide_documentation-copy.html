Text-to-PostgreSQL with Guardrails

A step-by-step guide to how this project was built — from an empty folder to a live, AI-powered SQL generator with a safety layer, real user accounts, and a live analytics dashboard. Written in plain language — no assumed experience needed.

What you'll find in this guide → Setting up the project from scratch → Connecting the app to real AI models → How the safety layer actually works → How the database is organized → Putting the app on the internet → Building a live analytics dashboard → How to actually use the finished app

What this app does

It turns a plain-English question into SQL — for any subject, any domain, not tied to one fixed database. Behind the scenes it:

  • Generates SQL (PostgreSQL language only) using a local AI model (Qwen, via LM Studio) with automatic fallback across OpenAI, Claude, and Gemini if one is unavailable
  • Checks every generated query through a guardrails layer before it's ever shown — SELECT-only, no destructive statements, no references to this app's own internal tables, no dangerous functions
  • Never executes anything — this is a generator with a safety layer, not a database client. Nothing is ever run against real data.
  • Lets people sign up with an email and password, or sign in with their Google account
  • Saves every question and its generated SQL encrypted, so the raw text can't be read by anyone browsing the database directly
  • Feeds a live Tableau dashboard showing usage trends and how often the guardrails actually catch something
  • Runs live on the internet — anyone with the link can try it

Multi-Provider Fallback

Rather than depending on one AI service, the app tries a configured order of providers until one works — and unlike a simple try/except, it remembers why each one failed, not just the last error:

def generate_sql(question: str) -> str:
    messages = build_messages(question)
    order = [os.environ.get("LLM_PROVIDER", "lmstudio")]
    order += [p.strip() for p in os.environ.get("LLM_FALLBACK_ORDER", "").split(",") if p.strip()]

    failures = []
    for provider in order:
        try:
            raw = PROVIDERS[provider](messages)
            return _clean_sql(raw)
        except Exception as e:
            failures.append(f"{provider}: {e}")
            continue

    raise RuntimeError(f"All LLM providers failed - {' | '.join(failures)}")
This mattered in practice: an early version only kept the last provider's error, which once hid a Gemini "high demand" 503 that was actually masking a missing API key failure earlier in the chain. See Troubleshooting.

On your own machine, lmstudio is first with hosted providers as backup. On Render, LLM_PROVIDER is set directly to a hosted provider, since Render can't reach LM Studio running on your laptop.

Guardrails

How Guardrails Work

Every piece of AI-generated SQL is parsed into a real syntax tree with sqlglot and inspected structurally — never checked with regex or keyword matching, which is trivial to bypass with comments, casing tricks, or whitespace.

  1. Must parse as valid SQL — anything that fails to parse is blocked
  2. Must be exactly one SELECT statement — any INSERT, UPDATE, DELETE, DROP, ALTER, TRUNCATE, or GRANT is refused outright, checked at the AST root node type
  3. Can never reference user or query_history — this app's own internal tables, permanently off-limits however the question is phrased
  4. No disallowed functions — a short blocklist (pg_sleep, pg_read_file, dblink, and similar) covers functions with no place in an ordinary query
  5. Stacked statements are blocked as a side effect of rule 2 — SELECT ...; DROP ...; doesn't parse as a single top-level Select node
  6. Row limits are capped, never added — an excessive LIMIT gets clamped to 200; a query with no limit (or an aggregate that naturally returns one row) stays exactly as generated
cte_names = {cte.alias.lower() for cte in parsed.find_all(exp.CTE)}
tables = {t.name.lower() for t in parsed.find_all(exp.Table)} - cte_names

if tables & NEVER_EXPOSE:
    return None, f"Query touches a protected table: {sorted(tables & NEVER_EXPOSE)}", "blocked"

That CTE-exclusion line matters: a WITH user AS (...) clause shouldn't be a false positive just because it shares a name with a protected table — but the check still catches the real attack, a CTE whose body still selects from the actual protected table.

What Gets Blocked

ExampleWhy
DROP TABLE employeesNot a SELECT statement
SELECT * FROM "user"References a protected internal table
SELECT * FROM a; DROP TABLE a;Multiple statements
SELECT pg_sleep(10)Disallowed function
WITH t AS (SELECT * FROM "user") SELECT * FROM tStill blocked — the CTE body still touches a protected table
Even a blocked query's generated SQL is still shown to the user, alongside the reason — transparency about what the AI attempted carries no risk here, since nothing was ever going to be executed either way.

Database

Setting Up Neon

  1. Sign up free at neon.tech
  2. Create a new project — Neon gives back a connection string: postgresql://user:pass@host/dbname?sslmode=require
  3. That one connection string is used everywhere — local development and the live app both point at the same database

Connecting the App

app.config["SQLALCHEMY_DATABASE_URI"] = os.environ["DATABASE_URL"]

Modern SQLAlchemy automatically resolves a plain postgresql:// URL to whichever driver is installed (psycopg2 or psycopg v3) — no need for a +psycopg suffix in the URL itself.

Database Tables

user — holds accounts

Email, a hashed password (null for Google-only accounts), Google ID if applicable.

query_history — the "message table"

One row per question. nl_question and generated_sql are encrypted — see Encryption. status (generated / blocked / error) and created_at are plain.

daily_stats — safe for analytics tools

Built by an ETL job from only the non-encrypted columns of query_history — daily counts per status, unique users. Contains no question or SQL text at all, so it's safe to point Tableau directly at.

query_history_export — optional, decrypted copy

A second ETL script can decrypt nl_question/generated_sql into this separate table, for richer Tableau exploration. See ETL Pipelines for the tradeoff this involves.

Splitting the data this way means the dashboard can show real usage trends — and even real question text, if you opt into the decrypted export — without the base query_history table ever holding anything a direct database browse could read.

Encrypting Questions & SQL

Both nl_question and generated_sql are scrambled before saving, using Fernet encryption. Anyone looking directly at the database sees only gAAAAABq..., never the real text.

python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

That key goes into .env as ENCRYPTION_KEY, exposed to the model via plain Python properties so encryption/decryption is transparent everywhere else in the code:

@property
def nl_question(self) -> str:
    return decrypt_text(self._nl_question)

@nl_question.setter
def nl_question(self, value: str) -> None:
    self._nl_question = encrypt_text(value)
This key must never be lost. If it's lost, every previously saved question and generated query becomes permanently unreadable.

Password Hashing

Different from encryption on purpose — hashing is one-way. Even the app itself can never recover a real password, only check a guess against the hash:

from werkzeug.security import generate_password_hash, check_password_hash

user.password_hash = generate_password_hash(password)
# later:
check_password_hash(user.password_hash, password_attempt)

Google-only accounts have password_hash = None, and the check correctly refuses any password for such an account rather than comparing against nothing.

  3. User support email: choose your own email
  4. Audience: choose External. Internal only works inside a Google Workspace company
  5. Contact information: enter your email, agree to the policy, then click Create
The app only asks for each person's email address and basic profile (the openid, email and profile scopes). These are the default scopes, so you don't need to add anything.

  1. Go to Google Auth Platform → Audience
  2. Under Test users, click Add users and enter the Gmail addresses that should be able to sign in (add your own first)
  3. When you are ready for anyone to use the app, click Publish app on the same page. Because the app only asks for the basic scopes, it does not need a Google review

Going Live

One Database, Local & Live

Unlike a typical setup with separate local and production databases, this project intentionally uses the same Neon database everywhere. The only thing that differs between local and live is LLM_PROVIDER — local defaults to lmstudio, Render is set directly to a hosted provider, since Render has no way to reach LM Studio running on your own machine.

Deploying to Render

  1. Sign up at render.com
  2. New + → Web Service → connect the GitHub repository
  3. Build Command: pip install -r requirements.txt
  4. Start Command: gunicorn app:app --timeout 90
  5. Add every secret from .env as an Environment Variable in Render's dashboard
If the service was created by clicking through Render's dashboard (not via a Blueprint sync), pushing an updated render.yaml may not automatically update the live Start Command — set it directly in the dashboard too, so there's no ambiguity about which one wins.

Automation

ETL Pipelines

Two separate scripts, each with a deliberately different relationship to ENCRYPTION_KEY:

etl_daily_stats.py — never touches the encryption key

Aggregates only the non-encrypted columns of query_history (status, user_id, created_at) into daily_stats. This script runs correctly with zero access to ENCRYPTION_KEY — it's structurally impossible for it to see decrypted content.

SELECT
    created_at::date,
    COUNT(*),
    COUNT(*) FILTER (WHERE status = 'generated'),
    COUNT(*) FILTER (WHERE status = 'blocked'),
    COUNT(*) FILTER (WHERE status = 'error'),
    COUNT(DISTINCT user_id)
FROM query_history
GROUP BY created_at::date
ON CONFLICT (stat_date) DO UPDATE SET ...

etl_decrypt_for_tableau.py — the one script that does decrypt

Optionally decrypts nl_question/generated_sql into a separate query_history_export table, for richer dashboard exploration. This is the one place in the whole project that writes decrypted text to disk outside the running app — paired with a scoped-down tableau_reader database role that can read this export table and daily_stats, but never the raw query_history or user tables.

Real tradeoff, not a hidden one: a decrypted export table means that data no longer benefits from encryption-at-rest. Weigh whether the richer exploration is worth it before enabling this second script — daily_stats alone is enough for trend/volume analysis with zero decrypted content anywhere.

Scheduling with GitHub Actions

.github/workflows/etl.yml runs the ETL automatically, once a day:

on:
  schedule:
    - cron: "0 3 * * *"   # daily at 3:00 AM UTC
  workflow_dispatch:        # also runnable manually from GitHub's Actions tab

jobs:
  run-etl:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install sqlalchemy "psycopg[binary]" python-dotenv
      - run: python etl_daily_stats.py
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}

1Add DATABASE_URL as a GitHub Actions secret

The workflow reads ${{ secrets.DATABASE_URL }} — this does nothing on its own until the secret actually exists in the repo:

  1. On github.com, open the repo → Settings tab → Secrets and variables → Actions
  2. Under the Secrets tab (not Variables), click New repository secret
  3. Name: exactly DATABASE_URL (case-sensitive) · Value: the same full Neon connection string from .env
Must be a repository secret, not an environment secret. Unless the workflow job declares environment: <name>, only repo-level secrets are visible to it — an environment-scoped secret of the same name silently won't be found.

2Test it

Actions tab → the workflow → Run workflow (uses the workflow_dispatch trigger — no need to wait for the 3am cron). The run should print a success line instead of raising RuntimeError: DATABASE_URL is not set.

Analytics Dashboard

Connecting Tableau

  1. Open Tableau and choose Connect → To a Server → PostgreSQL
  2. Enter the details from your Neon connection string: Server (the host), Port (5432), Database, Username and Password
  3. Tick Require SSL. Neon needs it for every connection
  4. Click Sign In, then drag the table you want onto the canvas: query_history or daily_stats (see below)
TableUse it for
query_historyThe full dashboard, including the Query Explorer table that shows each question and its SQL
daily_statsCounts only (one row per day). It holds no question or SQL text, so it is the safer choice for a dashboard other people will see
Never connect the user table. It holds emails and password hashes. Also, if encryption is on, the nl_question and generated_sql columns show as random letters (gAAAA...) in Tableau. They only read clearly when the text is stored as plain text.

Use a read-only database user

Don't sign in to Tableau with your database owner account. A workbook remembers the host and username, and an owner account can change or delete anything. Create a user that can only read, by running this in the Neon SQL Editor:

CREATE ROLE tableau_reader LOGIN PASSWORD 'choose-a-strong-password';
GRANT USAGE ON SCHEMA public TO tableau_reader;
GRANT SELECT ON daily_stats TO tableau_reader;
-- only if the dashboard needs the Query Explorer sheet:
GRANT SELECT ON query_history TO tableau_reader;

Then use tableau_reader and its password on the Tableau sign-in screen. Never give it access to the user table.
